Page layout

body.page provides an eleven-slot grid for application root layouts. The grid is fixed; slots opt in by carrying a pg-* class. Only pg-main is required; everything else is optional and collapses to zero when absent.

The eleven slots

Three full-width bands at the top, three at the bottom (well — two; the page footer plus optional main-footer), and a middle band split into three columns. The navigation and main columns each have their own internal header / body / footer rows. The aside spans the full middle band.

Anatomy

Wrap the application root in body.page and place children with their pg-* slot classes. Order in the markup doesn't matter — the grid template assigns each slot to its named area. 

<body class="page surface">
  <div class="pg-banner">…</div>
  <div class="pg-header">…</div>
  <div class="pg-subheader">…</div>
  <div class="pg-navigation-header">…</div>
  <nav class="pg-navigation">…</nav>
  <div class="pg-navigation-footer">…</div>
  <div class="pg-main-header">…</div>
  <main class="pg-main">…</main>
  <div class="pg-main-footer">…</div>
  <aside class="pg-aside">…</aside>
  <div class="pg-footer">…</div>
</body>

Semantic elements (<nav>, <main>, <aside>) on the slots that map to landmarks help with accessibility but are not required by the layout.

Slot semantics

Each slot has a default role. These are starting points, not constraints — content can migrate across slots at different viewports (see "Migrating content" below), but starting from the natural home keeps pages predictable.

Slot Track Default role
pg-banner full width Site-wide announcements, environment indicators, browser-upgrade nags.
pg-header full width Primary chrome. Brand, top navigation, account / settings.
pg-subheader full width Secondary chrome. Breadcrumbs, page title bar, persistent filters.
pg-navigation-header nav column top Workspace switcher, search input, section caption.
pg-navigation nav column body, scrolls Primary navigation. Section list, persistent in-app navigation.
pg-navigation-footer nav column bottom User profile, version info, sign-out.
pg-main-header main column top Page title, page-level tabs, action toolbar.
pg-main main column body, scrolls The content the user came for. The most important region; required.
pg-main-footer main column bottom Status bar, persistent action row, sync indicator.
pg-aside right column, scrolls Secondary context. Related items, activity feed, table of contents.
pg-footer full width Dock. Copyright, footer links, search hint.

Three regions scroll independently: pg-navigation, pg-main, and pg-aside. Every other slot pins. That's the default; per-instance overrides are normal CSS.

Opt-in via pg-* class

The grid template only assigns positions to direct children that carry a pg-* class. Children without one don't get a grid area and aren't placed in the template. Drawers, scripts, and other top-layer content can live as direct children of <body> without leaking into the layout. 

<body class="page surface">
  <main class="pg-main">…</main>

  <!-- These don't get a grid area; they live outside
       the page layout, in the top layer or hidden -->
  <dialog class="drawer left">…</dialog>
  <div popover class="drawer right">…</div>
</body>

The opt-in rule is a positive: slots are recognized by the pg-* prefix. The system does not actively hide unrecognized children — they participate in the document normally, just not in the page grid. Drawers handle their own positioning via position: fixed and the popover top layer.

Default padding

The .page rule applies padding: var(--gap) to every pg-* slot. The padding scales with the fluid --gap token — tight on phones, generous on TV-scale displays. Authors don't write inline padding on slots. 

.page {
  > [class^="pg-"] { padding: var(--gap) }
  /* … grid template and per-slot grid-area assignments … */
}

If a particular slot needs different padding, set it from CSS with a more specific selector. Per-instance inline padding overrides on slots opt out of the system's fluid scaling and lose consistency across the page.

Slot orientation rules

Each pg-* class is bound to its grid area and orientation. pg-navigation is always the left middle column; pg-aside is always the right; full-width slots always span the full width. Variants inside a slot can change its internal layout and width but not its position in the page.

Variants sharing a slot must share that slot's orientation. A pg-navigation can hold a full sidebar and an icon-only rail as siblings (both vertical, both in the left column), but not a sidebar and a horizontal top bar — the horizontal bar would belong in pg-header instead.

Responsive viewport classes

The .mobile, .tablet, and .desktop classes gate participation by viewport width. Default (no class) is always on. Adding any class restricts the element to matching viewports. Combine for ranges as unions: class="tablet desktop" means "everywhere except mobile." 

<!-- Visible only at desktop -->
<aside class="pg-aside desktop">…</aside>

<!-- Visible at tablet and desktop, hidden at mobile -->
<nav class="pg-navigation tablet desktop">…</nav>

<!-- Visible only at mobile -->
<button class="icon-btn mobile">☰</button>

Slots whose children don't participate at the current breakpoint collapse to zero. At mobile, <nav class="pg-navigation tablet desktop"> is hidden, so the entire navigation column track disappears and main expands to fill the freed space.

Cascade rule

A viewport class controls its element's display via revert-layer !important. That rule beats any display declaration on the same element from layout primitives, inline @scope blocks, or per-instance styles.

Authors must not put a layout primitive class (.row, .column, .grid, .flank, .hero, etc.) on the same element as a viewport class. The layout primitive's display will be silently overridden and the element will lay out with its native default. Wrap the content in a child element and put the layout primitive on the wrapper. 

<!-- Wrong — .column is silently overridden -->
<nav class="pg-navigation column tablet desktop">
  <a href="...">…</a>
</nav>

<!-- Right — wrapper carries the layout -->
<nav class="pg-navigation tablet desktop">
  <div class="column">
    <a href="...">…</a>
  </div>
</nav>

The coverage rule

Viewport classes partition the viewport range. Cover the full range when gating an element: a .mobile-only element disappears at tablet and desktop, leaving a hole unless something else fills the slot at those sizes. Think in partitions, not in isolated additions.

Most layouts settle into one of two patterns. A two-way split has one shape persistent across two breakpoints and another for the third (typical: persistent on desktop, drawer on mobile and tablet). A three-way split has a different shape per breakpoint, all sharing the slot's grid track. The next section shows both.

The duplication pattern

When a slot needs to look different at different viewports, author each shape and let viewport classes pick which is live. Drawers fill the breakpoints where the persistent slot is hidden.

Two-way case

The slot carries the viewport class. A page-level HUD with a FAB trigger opens the drawer at the breakpoints where the slot is hidden. 

<body class="page surface">
  <nav class="pg-navigation desktop">
    <!-- nav content -->
  </nav>

  <main class="pg-main">…</main>

  <!-- HUD overlay with mobile + tablet trigger -->
  <div class="hud" style="position: fixed; inset: 0;
                          pointer-events: none">
    <button class="↙ icon-btn mobile tablet"
            style="margin: 1rem"
            onclick="document.getElementById('nav-drawer').showModal()">
      ☰
    </button>
  </div>

  <dialog id="nav-drawer" class="drawer left hero surface">
    <div class="top">…search…</div>
    <div class="main">…links…</div>
    <div class="bottom">…user info…</div>
  </dialog>
</body>

On desktop, the persistent pg-navigation shows in its track and the FAB is hidden. On smaller screens, the slot's track collapses, the FAB appears, and tapping it opens a modal drawer that composes .drawer (positioning + animation), .hero (internal three-region layout), and .surface (paint).

Three-way case

The slot holds multiple persistent shapes nested inside, gated by viewport classes. The drawer covers the remaining breakpoint. 

<nav class="pg-navigation">
  <section class="desktop">
    <!-- full sidebar with text labels -->
  </section>
  <section class="tablet">
    <!-- narrow icon-only rail, same vertical orientation -->
  </section>
</nav>

<dialog id="nav-drawer" class="drawer left hero surface">
  <!-- drawer shape, opened by mobile-only FAB -->
</dialog>

Each variant typically wants its own internal layout. Use inline @scope on a wrapper <div> for layout rules so the cascade rule above doesn't silently override display.

Drawers

Two flavors, distinguished by element type and chosen by intent.

Modal drawer — <dialog>

Use when the drawer demands full attention: navigation, confirmations, focused tasks. Opens with showModal(), has a dim backdrop, traps focus, makes the page underneath inert. 

<dialog class="drawer left">…</dialog>

<button onclick="document.querySelector('dialog.drawer.left').showModal()">
  open nav
</button>

Non-modal drawer — <div popover>

Use when the user needs to keep working on the page while the drawer is open. The canonical case: a form referencing content elsewhere on the page. Opens via popovertarget on a button (no JS) or element.showPopover(). 

<div id="filters" popover class="drawer right">…</div>

<button popovertarget="filters">open filters</button>

Animation and positioning are identical between the two flavors; only modality differs. Drawer positions are .left, .right, .top, .bottom. Source order: drawers should be placed after the page slots, not nested inside a slot — they live in the top layer or as positioned popovers and don't need a place in the grid.
